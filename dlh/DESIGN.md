# Целевой Lakehouse — проект

Для волны 1 нужны целевые `dlh.oil_stg`, `dlh.oil_dds`, `dlh.oil_mart` с бизнес-таблицами field/well/production_day и независимым `v_field_production`. Логические ключи и единицы совпадают с GP, физические свойства GP не переносятся автоматически. GP PK, distributed by и функции PL/pgSQL не являются возможностями Iceberg; события U/D и инварианты реализуются и проверяются в Spark с явным контрактом, идемпотентностью и snapshot manifest. Разделение по годам/дате — после измерения реального размера, не механическое копирование распределения GP.

Волна 2 — hub/link/satellite простоя, факт интервалов и агрегат простоев, затем `v_field_performance`; использует уже перенесённые общие измерения и факт добычи на одной проверенной границе. Подготовлен draft `production_job.py` для первой волны; Iceberg sink и Spark job в целевом runtime не проверены, поэтому это проект, а не работающее внедрение.

LakeKeeper регулирует доступ к каталогу; отдельно настраиваются права S3, Spark/Cedrus, CIAM и Superset. Структура snapshots по каждой таблице сохраняется в release manifest; атомарной транзакции между всеми Iceberg-таблицами не предполагается. Не запускать перенос до утверждения и наличия валидной согласованной границы GP/Kafka. Для DDL нужны подтверждение версий движка, каталога и поддерживаемых типов timestamp/decimal; шаблонные CREATE не выдаются за проверенные.
