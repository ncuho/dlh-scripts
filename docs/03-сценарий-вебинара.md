# Сценарий вебинара: миграция бизнес-цепочки

Состояние на 21 ноября 2026. Данные синтетические, UTC, нефть измеряется в тоннах. Первая волна — добыча по месторождениям — перенесена как фиксированный срез; вторая — эффективность и простои — остаётся в Greenplum. Это демонстрационный стенд: автоматическая постоянная синхронизация и промышленная отказоустойчивость не подтверждены.

1. **Контуры.** Покажите Greenplum в VK Cloud и сервисы VK Data Platform. Greenplum — исходное хранилище; Iceberg на объектном хранилище с LakeKeeper и CedrusData Engine — целевой контур.
2. **Сервисы.** Откройте Kafka, Kafka Connect, Greenplum, Airflow, LakeKeeper, CedrusData Engine, Data Catalog и Superset; версии и доступность покажите по текущему состоянию интерфейсов. Один Kafka broker с RF=1 не демонстрирует HA.
3. **Исходный поток.** Покажите генератор, topic `oil.events.v1` и работающий `webinar-oil-gp-ingest`. Поток принимает события в `oil_stg`; генератор в обычном состоянии остановлен, чтобы данные на зафиксированной границе не менялись.
4. **Слои Greenplum.** Представьте staging для приёма, учебную адаптацию Data Vault 2.0 в `oil_dds` и звезду в `oil_mart`. Объясните роли таблиц событий, hub/link/satellite, измерений, фактов и агрегатов, а также функций обработки.
5. **Целевой контур.** Покажите Iceberg-таблицы, управление каталогом LakeKeeper и чтение через CedrusData Engine. SQL первой волны выполнялся через Cedrus; проект Spark есть в репозитории, но не проверен на живом runtime.
6. **Каталог и lineage.** Начните с отчёта Superset и проходите назад через графики, витрины, функции, исходные таблицы, connector и topic. Связи внесены вручную; полнота поколоночного lineage от JSON до BI в UI ещё не подтверждена, поэтому не представлять его как автоматически извлечённый.
7. **Выбор волны.** Первую цепочку добычи используйте как пример результата. Для демонстрации переноса выберите вторую цепочку: события простоев → staging → DDS → факты и витрина эффективности → отчёт Superset; общие сущности добычи уже есть в DLH.
8. **Стратегия.** Определите состав объектов, владельца, идентификатор выпуска, срез, правила replay, сравнения и возврата. Контрольный барьер нужен для всех источников записи, не только Kafka consumer.
9. **Исходный код.** В репозитории Greenplum откройте DDL, функции загрузки, обработку событий, SQL витрин и Airflow DAG. Покажите, что ручной DAG `oil_gp_release` публиковался и имеет успешный проверочный запуск; сейчас он приостановлен.
10. **Целевые объекты.** В репозитории DLH покажите фактические SQL первой волны и проект `sql/wave2_migration.sql`. Проект второй волны не исполнялся целиком и не должен рассматриваться как готовый автоматический CDC.
11. **Сопоставление архитектур.** Объясните перенос бизнес-правил и семантики данных, замену физического устройства таблиц на Iceberg и сохранение отчёта как бизнес-контракта. Распределение и индексы GP не переводятся в Iceberg напрямую.
12. **Граница.** Для существующей первой волны покажите manifest: источник был остановлен, exclusive offsets по партициям — 5170, 5196 и 5159; GP checkpoints совпали. Для новой волны нужна новая подтверждённая граница с учётом всех writers и удержания Kafka.
13. **Первичная загрузка.** Покажите фактические CTAS первой волны из GP через Cedrus. На новой волне данные нужно загружать только из согласованного снимка, контролируя общие зависимости; несколько Iceberg commits не образуют общую транзакцию.
14. **Сверка.** Откройте `quality/wave1-reconciliation.json`: 14 объектов прошли двусторонний `EXCEPT ALL` с нулём расхождений. Для второй волны дополнительно нужны проверка ключей, NULL, бизнес-сумм и одна согласованная граница.
15. **Бизнес-логика.** Сопоставьте GP SQL и функции с целевыми SQL/Spark-проектами. Для факта простоев есть read-only сравнение расчёта с GP без расхождений, но оно не доказывает готовность всего target pipeline.
16. **Расчёт и публикация.** Покажите существующий GP DAG и результаты витрин. Целевой DAG, барьер публикации всех таблиц и тест полного перерасчёта ещё необходимо реализовать и проверить до живой демонстрации их запуска.
17. **BI.** Откройте две панели GP и копию панели добычи на DLH. Целевая панель сейчас использует физическую `dlh.oil_mart.agg_field_day`: доступ к аналогичному view возвращает отказ; результат графиков проверен через API, но не мышью в браузере.
18. **Дельта.** Объясните применение событий после exclusive offsets по каждой партиции с отдельной consumer group, проверкой retention, дедупликацией и правилами обновления/удаления. Для бизнес-цепочки этот механизм пока не настроен: не запускать как готовый сценарий.
19. **Параллельный ingestion.** После готовности и проверки независимого Iceberg sink можно добавить целевого потребителя, не отключая GP sink. Порядок только внутри партиции, а совпадение Kafka offsets и транзакционного среза GP требует явного fencing всех writers.
20. **Доступы.** Сопоставьте исходные роли GP с ролями и политиками LakeKeeper, правами на S3 и доступом через Cedrus; отдельно проверьте доступ к панели Superset. Права нельзя считать перенесёнными до фактических проверок разрешённых и запрещённых операций.
21. **Итоговая сверка.** На одной границе сравните данные, промежуточные результаты и бизнес-показатели, затем получите согласование владельца отчёта. Старый GP остаётся источником истины; при ошибке чтение возвращается на исходную панель.
22. **Следующая волна.** В Data Catalog выберите следующую цепочку и проверьте общие зависимости и границы. Зафиксируйте результаты, нерешённые вопросы мониторинга и условия перехода к постоянному ingestion.

## Перед живым запуском второй волны

Необходимы: отдельный проверенный sink и его права; replay и обработка U/D с идемпотентностью; сохранённые offset/retention; работающее исполнение целевых расчётов; согласованная публикация и end-to-end сверка; проверенный rollback и BI-доступы. На данный момент это незакрытые работы. PXF и внешние таблицы не обязательны для данной Kafka-цепочки; их доступность не подтверждена, поэтому демонстрировать их как установленный компонент нельзя.
