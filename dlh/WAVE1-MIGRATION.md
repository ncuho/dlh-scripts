# Перенос первой волны: подготовленный маршрут

Это проект исполняемого маршрута, а не подтверждённая интеграция. GP JDBC из Spark/Jupyter, PostgreSQL JDBC driver в classpath, TLS и Iceberg API на целевом runtime не проверены. Во время подготовки бизнес-данные не переносятся. Текущий код не использует CedrusData для чтения GP: основной предлагаемый маршрут — Spark JDBC → Iceberg. CedrusData можно использовать для контрольной SQL-сверки при наличии подтверждённого коннектора GP. Не утверждать поддержку любого маршрута без проверки.

## 1. Общая граница

До baseline согласовать owner/scope и остановить всех writers, которые могут менять GP в обход события или принимать новые события. Дождаться долговечной обработки событий GP, зафиксировать идентичность Kafka кластера и topic, конечную позицию **exclusive** по каждой partition, GP checkpoint и состояние ошибок. Снять транзакционно согласованный `pg_dump` после финального apply/refresh и восстановить в отдельную базу; убедиться в успешном восстановлении, проверить целостность, permissions и запрет изменений на ней. При необходимости проверить данные GP в копии и зафиксировать идентификатор backup/restore. Фактическая блокировка записи, граница offsets, роли и тождественность копии исходной волне подтверждаются оператором и audit evidence, а не полями JSON.

Разные вызовы Spark JDBC открывают отдельные соединения. Это не один exported GP transaction snapshot. Повторное чтение безопасно только при реально неизменяемой восстановленной копии и действующей блокировке всех писателей на весь период; иначе counts и таблицы могут относиться к разным состояниям. Проверить, что копия содержит именно новую нефтегазовую схему, а не старый baseline. Добавить retention Kafka, fence и план rollback.

Подготовить защищённый JSON без секретов:

```json
{"cut_id":"wave1-cut-001","snapshot_id":"verified-pg-backup-id","freeze_evidence":"approved-audit-record", "source_cluster":"gp-cluster-id","source_database":"oil_frozen_clone","kafka_end_offsets_exclusive":{"oil.events.v1":{"0":100,"1":100}}}
```

Это **пример**, значения не означают реальную границу. Программа проверяет только форму, запрещает source database `og_dwh` и системные имена; она не устанавливает freeze, не валидирует backup и не доказывает соответствия offsets. Не включать в план пароли и токены.

## 2. Изолированная загрузка восьми DDS-объектов

Согласовать release ID, подготовить `dlh.oil_dds` и `dlh.oil_mart`, роль для создания только release-таблиц, отдельный GP read-only пользователь только на frozen clone и сетевой путь. У Spark JDBC параметры задаются через защищённое окружение `OIL_GP_JDBC_URL`, `OIL_GP_USER`, `OIL_GP_PASSWORD`; URL должен иметь `sslmode=verify-full` и `sslrootcert` в filesystem драйвера, без user/password в URL. Проверьте hostname сертификата, возможность чтения сертификата и наличие драйвера. Код не проверяет самостоятельно права доступа и наличие других писателей GP. Не печатать окружение в журнал.

`python stage_wave1_dds.py --plan approved.json --release-id wave1_001 --output-manifest dds-release.json` только валидирует план. Явный `--execute` создаёт новые таблицы и может быть использован только по плану вебинара. Указанный `--output-manifest` не должен существовать. Порядок: `hub_field`, `hub_well`, `hub_production_day`, `link_well_field`, `link_production_day_well`, `sat_field`, `sat_well`, `sat_daily_production`. Каждая таблица получает имя `dlh.oil_dds.r_wave1_001_<object>`, загружается из GP одной JDBC partition и имеет отдельный Iceberg commit. Код проверяет количество и сохраняет snapshot ID; полное равенство данных это не доказывает. Бизнес-таблицы новой цепочки без префикса не изменяются.

Быстрый подсчёт перед записью и повторное чтение при записи используют разные JDBC соединения; неизменяемость source обязательна. Размеры и производительность измерить до показа. Для больших таблиц понадобится другое partitioned чтение поверх гарантированно неизменяемого снимка; не включать его без проверки модели консистентности и нагрузки.

## 3. Расчёт четырёх объектов и допуск

После подтверждения всех восьми input snapshots использовать сформированный DDS release manifest напрямую: `python production_job.py --input-manifest dds-release.json` — dry-run. После DQ при наличии fencing оператор запускает `--stage-release wave1_001 --release-manifest mart-release.json`. Порядок новых таблиц: `dim_field`, `dim_well`, `fact_well_day`, `agg_field_day`; вход — пять версионированных таблиц из подготовленного manifest. Исходные GP функции полностью не заменяются автоматической трансляцией: нужно сравнить бизнес-правила, схему, timezone/DECIMAL и DQ на данных одной границы. Никакого переключения BI не происходит.

Для допуска сравнить 12 объектов с frozen GP на snapshot ID из DDS/MART manifest: число, набор полей и типы, NULL, уникальность ключей, отрицательные значения, версии, затем полное мультимножество строк и бизнес-агрегаты. `quality/03_wave1_reconcile.sql` — черновой набор EXCEPT ALL, в нём нужно подставить верифицированные GP FQN и release ID и обеспечить чтение точных Iceberg snapshots либо подтвердить, что heads не менялись. Проверить type coercion и поддержку EXCEPT ALL на соединении. Сравнить суммы нефти по дням и месторождениям, количество активных well-days, null при нулевом знаменателе. Принять или отклонить публикацию с владельцем отчёта.

Код формирует новый файл release manifest только после полного завершения каждого этапа; таблицы коммитятся по одной. При ошибке часть может уже существовать, даже если лог не успел её зафиксировать: перечислить все 8 или 4 ожидаемых имён. Не перезаписывать и не удалять чужие объекты; разбор и cleanup только после проверки прав, владельца, snapshots, зависимостей и внешнего fence. Чтобы исключить гонки, понадобится проверенный внешний single-writer lock и защита release-таблиц от записи третьих лиц.

## 4. После baseline

Начать delta ingestion от зафиксированных exclusive offsets на выделенной consumer group; убедиться, что Kafka сохранила нужные события и что sink поддерживает update/delete и идемпотентную обработку. Текущие скрипты это не реализуют. Повторить расчёт и сверку на новой единой границе, отдельно проверить роли LakeKeeper/S3/Cedrus/Superset и создать/переключить копию отчёта после бизнес-допуска. Вторая цепочка простоев остаётся в GP до следующей волны.
