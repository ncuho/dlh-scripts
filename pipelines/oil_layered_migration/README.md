# Прямая миграция нефтедобычи

`oil_layered_migration` выполняет только INITIAL одной task `migrate_and_validate`. Конфигурация `{"mode":"initial"}`. Одно native GP-подключение удерживает REPEATABLE READ READ ONLY для всех 20 объектов. Источник продолжает работать; служебная схема bridge_capture и промежуточная транспортная таблица не нужны.

`oil_gp_snapshot.py` выбирает непрерывный уже применённый префикс C0: READY-хвост не включается в историю, APPLIED Stage согласован с DDS и витринами. `oil_direct_source.py` читает все 20 объектов из одного snapshot порциями по 500 строк и отправляет типизированные INSERT через Cedrus прямо в Bronze/Silver/Gold. INITIAL не использует Spark. Два GP-view в цели материализуются как таблицы.

`oil_layered_plan.py` задаёт зависимости, колонки и DQ. `Runner.prepare()` проверяет пустые цели и фиксирует C0; `materialize()` допускает объект только после VALIDATED у родителей, загружает и сверяет его; `validate_all()` проверяет полный набор из 20 объектов и 65 проверок; `finish()` сохраняет READY. При ошибке `compensate()` очищает подтверждённые собственные записи в обратном порядке. Неизвестный исход требует разбора. `DirectSource.close()` закрывает исходную read-only транзакцию.

После INITIAL единственный `oil_dlh_release` обрабатывает события Spark в тех же таблицах. Ручной mode=catchup фиксирует GP C1 и выполняет 58 проверок, включая сверку Gold с GP; режим release по расписанию читает только raw и выполняет 53 проверки. MERGE Bronze/Silver исключает повторные записи, Gold пересчитывается атомарно по таблице. Checkpoint и serving публикуются последними; единой ACID-транзакции всех Iceberg-таблиц нет.

Source batch_id сохраняются в INITIAL. Новые Lakehouse доставки получают отдельные отрицательные batch_id из partition/offset. Сначала создаётся batch_control, затем Stage/DDS. Бизнес-ключи и hash-key сохраняются. Receipts содержат подписи исходных строк, snapshots и повторяемые SQL-проверки; полные исходные строки в receipt не сохраняются.
