# Сквозной перенос добычи по слоям

`oil_layered_runtime.py` исполняет INITIAL/REFRESH, `oil_layered_plan.py` задаёт 20 объектов и настоящие зависимости из SQL и проверок. Исполняемый SQL хранится в соседних папках `production_online/<symbol>`, отдельные phase-aware проверки — в `checks/` каждого объекта. `oil_layered_cedrus.py` использует существующую сервисную авторизацию Cedrus MCP.

Исходный `oil_stg` отображается в `bronze`, `oil_dds` — в `silver`, `oil_mart` — в `gold`. INITIAL сохраняет имена исходных объектов: `gold.fact_well_day`. REFRESH строится отдельно в таблицах с суффиксом `_next`. Landing-поток пишет `bronze.__raw_events` и не очищается компенсацией.

Каждая задача проверяет завершение родителей, пустоту цели и её определение/location; выполняет один INSERT в Cedrus или Spark; фиксирует snapshot и исполняет проверки. Для INITIAL суммарно 60 проверок, для REFRESH — 53. Расчёт ключей, версий и интервалов остаётся в SQL/Spark. Airflow управляет зависимостями и не заменяет вычислительный движок.

Компенсирующий откат восстанавливает пустое содержимое только кандидатных таблиц текущего запуска, в обратном порядке. Он не отменяет события Kafka, обработку GP, raw или принятый INITIAL во время REFRESH. Snapshot history не стирается: это компенсация данных, а не распределённая ACID-транзакция. Кандидат имеет одного писателя — этот DAG, автоматические retries отключены.

При UNKNOWN_OUTCOME, изменившемся snapshot/location или сбое самой компенсации выпуск переходит в MANUAL_RECONCILE. Данные не удаляются вслепую и отчёт не переключается. Нужно сверить query/kernel receipt и актуальное состояние таблицы. Успешная компенсация оставляет итоговый DAG run неуспешным.

Файлы READY в `/opt/airflow/logs/oil_layered_migration/` содержат реальные запросы, snapshots и сверки. Они не хранят секреты и не публикуются в Git. Код не переключает Superset автоматически: после READY оператор проверяет доступы и бизнес-результат, затем меняет binding отчёта.

REFRESH по умолчанию повторно читает десять offsets до C0 в каждой партиции. Логическая граница остаётся C0–C1, а `read_start` явно показывает перекрытие. Stage исключает повторы координат, DDS исключает повторы event_id, новая бизнес-версия применяется по entity_version. Разный payload для одинаковой координаты/event_id не замалчивается, а блокируется DQ. Можно задать `overlap_offsets` от 0 до 10000 в конфигурации DAG. Timestamp-overlap не заменяет CDC для изменений GP вне Kafka.

Например, C0=100 и C1=110 при overlap_offsets=10 дают чтение offsets 90–109: 90–99 повторно сверяются, 100–109 дополняют историю. Это позиции Kafka, а не минуты. Не используем фильтр по времени начала транзакции или event_time как доказательство полноты. Capture сериализуется с GP sink через checkpoint; поздний коммит учитывается по применённой позиции.

SQL MERGE здесь не выполняется: отдельный `_next` строится из INITIAL и перекрывающегося окна с детерминированной дедупликацией. Принятый отчёт остаётся доступным до READY и проверки доступа. События после C1 остаются в raw для следующего цикла. Кратковременное ожидание GP writers во время capture возможно; непрерывное чтение отчёта не означает нулевую задержку записи и нулевой lag.
