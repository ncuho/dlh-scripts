# Расчёт первой волны: подготовка к проверке

`production_job.py` читает пять целевых DDS-таблиц и формирует `dim_field`, `dim_well`, `fact_well_day`, `agg_field_day` по бизнес-логике GP. По умолчанию выполняется только dry-run без записи. Результат включает checks, counts и небольшие sample rows; отсутствие данных или ошибка качества останавливают расчёт. Это проект: синтаксис Spark/Iceberg, CIAM, `dp103_spark`, права и эквивалентность результатам GP на стенде не подтверждены.

Для воспроизводимого расчёта оператор готовит manifest: `{"cut_id":"approved-cut","snapshots":{"sat_field":101,"sat_well":102,"sat_daily_production":103,"link_well_field":104,"link_production_day_well":105}}`. Числа — примеры, не реальные snapshots. Снимки вводятся через `--input-manifest`; известные ID ещё не подтверждают согласованность между таблицами, которую должен доказать upstream. Все снимки должны сохраняться на протяжении расчёта и сверки.

После утверждения и технического fencing один writer может вызвать `python production_job.py --input-manifest input.json --stage-release wave1_001 --release-manifest release.json`. Создаются четыре новые таблицы с префиксом `dlh.oil_mart.r_wave1_001_`; после проверок создаётся новый локальный manifest с входными ID, хешем input manifest и ID выходных snapshots. Не происходит записи в итоговые витрины и переключения потребителей. Каждый Iceberg commit независим, поэтому ошибка может оставить частичные таблицы. Транзакционный registry/переадресация и права от изменения после stage — внешние обязанности; при ошибке исследовать все четыре возможных имени до уборки. Сравнение только числа строк не доказывает равенства значений: после записи нужны проверка схем, выборок, мультимножеств, бизнес-агрегатов и допуск владельца по единому cut.

Настоящие ingestion/CDC, фиксация GP snapshot по Kafka offsets, запуск Spark под системным аккаунтом и подключение BI находятся вне скрипта. Команды выше не выполнялись.
